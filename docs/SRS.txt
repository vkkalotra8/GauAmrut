1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) defines the complete functional and non-functional requirements for GauAmrut, a multilingual, mobile-first, multi-tenant dairy-delivery and billing platform. It is written for the full-stack team building the product from zero — there is no existing codebase — and, together with Section 8 (Deployment), is sufficient to design, build, test, and run a live production application on Vercel and Render with MongoDB Atlas as the database.
This document is binding: “shall” / “must” marks a mandatory requirement; “should” marks a strong recommendation; “may” marks optional behavior. Where any other artifact conflicts with this SRS, this SRS governs until formally revised.
1.2 Scope
GauAmrut lets independent milk vendors (“milkmen”) manage customers, twice-daily delivery entry, rate-based billing, payment collection, products/orders, disputes, notifications, and reports, while customers get transparent self-service visibility into their own account, and administrators operate the platform through permission-scoped controls.
In scope for the initial production release: OTP-based registration and JWT authentication; milkman and customer profile/lifecycle management; daily delivery entry (online and offline-capable); vacation/extra adjustments; monthly billing and payment reconciliation; products and orders; disputes; in-app, real-time, email, and WhatsApp notifications; PDF/CSV exports; an admin console; and a responsive, installable, accessible, localized (English/Hindi/Gujarati) Progressive Web App backed by a REST + WebSocket API.
Out of scope for the initial release: native mobile apps, IoT hardware integration, card custody, inventory/procurement, payroll, GPS route optimization, tax filing automation, simultaneous multi-milkman membership per customer, and AI-based demand forecasting.

2. Overall Description
2.1 Product Perspective
GauAmrut is a new, standalone, cloud-hosted, multi-tenant SaaS product built entirely from this specification. It consists of a single-page React application (frontend), a Node/Express REST + WebSocket API (backend), and MongoDB as the sole system of record, supported by Redis, email, and WhatsApp integrations.
2.2 Product Functions (Summary)
Milkman and customer registration, OTP verification, and JWT-based login.
Milkman business identity, unique linking code, customer directory, and route ordering.
Customer onboarding by code, history claim, and single-tenant linkage.
Daily delivery entry (single and batch) with offline queueing and conflict handling.
Vacation and extra delivery adjustments with audit trail.
Monthly bill generation, payment recording, payment requests, and receipts.
Product catalogue and order management with price/quantity snapshots.
Dispute lifecycle management with evidence and resolution tracking.
In-app, real-time (WebSocket), email, and WhatsApp notifications.
PDF and CSV report generation and export.
Permission-scoped admin console: users, operations, payments, products, disputes, analytics, settings, backups, audit log, access control.
2.3 User Classes and Characteristics
Full actor detail is in Section 3. In summary: Milkmen are primary operators, frequently on mobile devices outdoors on unreliable connectivity, needing fast low-friction entry. Customers consume transparency and need simple, trustworthy views of deliveries and money. Administrators need safe, permissioned, auditable controls.
2.4 Operating Environment
The application is delivered as a responsive web app (PWA) accessed via modern browsers on mobile and desktop. Production hosting target: static frontend build on Vercel; Node backend as a Render Web Service; MongoDB Atlas as a managed replica set; Redis as a managed add-on; outbound integrations for SMTP email and the WhatsApp Cloud API. Full deployment detail is in Section 8.
2.5 Design and Implementation Constraints
MongoDB is the only database and must run as a replica set (never standalone) because registration, billing, and payment require multi-document transactions.
Money must be represented as integer minor units or Decimal128 — never native JavaScript floating point — for any accounting value.
Timestamps are stored in UTC; service dates are interpreted in Asia/Kolkata (configurable) for display and business logic.
Every tenant-owned document carries milkman_id; the backend derives and verifies tenant context from the authenticated session and never trusts a client-supplied tenant ID.
The frontend builds and runs entirely as static assets suitable for Vercel; it must not depend on a Node server at runtime.
The backend is a stateless Express process suitable for horizontal scaling on Render, with no in-memory session or job state that would break under multiple instances.
2.6 Assumptions and Dependencies
A MongoDB Atlas project and cluster are provisioned before backend deployment.
A transactional email provider (SMTP-compatible, e.g., SendGrid / Postmark / SES) and WhatsApp Cloud API credentials are available before notification features are exercised end-to-end in production.
Custom domains, if used, are purchased/managed outside this system and pointed at Vercel/Render per Section 8.
3. Actors and Access Control
Authorization is enforced entirely on the backend. A request is valid only if the authenticated identity matches the resource's owning tenant/customer, or the authenticated admin holds the specific named permission for that action. Knowing a resource's ID must never by itself grant access.
Actor
Access and Responsibilities
Milkman
Owns one tenant. Rapid daily route entry, customer management, collections, product/order fulfilment, reports. Often on a phone, outdoors, on unreliable connectivity.
Customer
Linked to exactly one milkman. Views delivery history and balance, submits pause/extra requests and payment claims, places product orders, raises disputes.
Admin — super_admin
Full platform authority across all modules, including access control and irreversible actions (with reason/audit).
Admin — operations
Manages users/lifecycle, dairy operations, products, disputes, analytics.
Admin — finance
Manages payments and financial analytics.
Admin — support
Read visibility into users and disputes for customer support.

Rule: milkman-scoped requests must match the authenticated profile's own milkman_id; customer-scoped requests must match the authenticated customer; nested resources (e.g., a delivery under a customer) must match the same tenant/customer chain; admin routes require the specific named permission, not just an admin role flag.

4.2 Onboarding Journeys
4.2.1 Milkman Onboarding
Flow: collect identity, contact, password, and business name → send OTP → verify OTP → atomically create user and milkman profile → generate a collision-safe 8-character milkman code → redirect to dashboard → prompt to add customers, rates, defaults, and route. A failure at any step shall leave no orphaned user or profile record (the create step must be transactional).
4.2.2 Customer Onboarding
Flow: customer enters a milkman code → system resolves and displays the business name for confirmation → OTP verification → if unlinked delivery/billing history exists for that contact, offer a safe claim step → link the customer to exactly one milkman → from that point the customer only ever sees that tenant's data.

API conventions: JSON envelope of { success, data, meta? } on success and a machine-readable { error: { code, message } } on failure; bounded pagination; ISO 8601 dates; explicit money amount + currency fields (never bare floats); an Idempotency-Key header required on all consequential writes (delivery entry, payment recording, payment approval); a correlation/request ID on every response for support and log tracing. Passwords, hashes, secrets, and stack traces are never exposed. The API is documented with OpenAPI 3.1, including role, permission, tenancy, request/response schema, and error cases for every endpoint.

6. Non-Functional Requirements

ID
Requirement
NFR-SEC-01

Auth/OTP rate limits shall be enforced across distributed instances (via Redis); settings and backups shall be encrypted; service credentials shall follow least privilege.
NFR-SEC-06
Personally identifiable information shall be minimized, masked in logs, retained per policy, and deletable on request; secrets shall never be logged.
NFR-SEC-07
Payment collection shall be provider-hosted; card credentials shall never be stored by the platform.
NFR-SEC-08
Dependencies and deployment images shall be scanned for known vulnerabilities; audit logs shall be tamper-resistant.

ID
Requirement
NFR-PERF-01

7. System Architecture and Technology Stack

  -> domain services and policy layer
  -> repository layer + transaction / idempotency boundary

MongoDB (Atlas-hosted) is the sole database, accessed through Mongoose. 8.4 Database Deployment (MongoDB Atlas)
NFR-DEPLOY-11: The database shall be an Atlas-managed replica set (the Atlas default topology), sized appropriately for the environment (shared tier acceptable for development/staging; dedicated tier recommended for production).
NFR-DEPLOY-12: Network access shall be restricted to Render's egress IPs where feasible; where Render's egress IPs are not static, access shall be restricted at the database-user and TLS level and broad IP ranges shall be treated as a documented, reviewed exception rather than a default.

NFR-DEPLOY-15: The connection string shall enforce TLS and shall be stored only as the MONGO_URI environment variable on Render, never committed to source control.
8.5 Redis, Email, and WhatsApp
Redis: a managed Redis instance (Render Redis add-on or an external provider) reachable via a REDIS_URL environment variable on the backend.
Email: an SMTP-compatible transactional email provider (e.g., SendGrid, Postmark, Amazon SES) configured via SMTP_* environment variables.
WhatsApp: WhatsApp Cloud API credentials (token, phone number ID, template names) configured via WHATSAPP_* environment variables, used only by the outbox worker.

8.7 CI/CD and Release Process
Source control: a single GitHub repository with frontend/ and backend/ workspaces, or two repositories, as the team prefers — either way, Vercel watches the frontend path and Render watches the backend path on the same main branch.
Continuous Integration: on every push/PR, run lint, unit tests, integration tests, and build for both workspaces; block merge on failure (NFR-MNT-02).
Continuous Deployment: merges to main trigger an automatic Vercel production deploy and an automatic Render deploy of the backend; pull requests get an isolated Vercel preview URL for manual QA.
Rollback: both platforms retain prior successful deployments; a rollback is a one-click redeploy of the previous build on either platform (NFR-OPS-03).
Custom domains: once approved, a custom domain is attached in Vercel for the frontend and, optionally, in Render for the API; both platforms provision TLS certificates automatically.
8.8 Go-Live Checklist
MongoDB Atlas replica set provisioned, least-privilege user created, network access reviewed, backups enabled and a restore rehearsed.
All required backend environment variables set in Render; all required frontend environment variables set in Vercel.
CORS_ORIGINS on Render contains only the real Vercel production domain (and preview pattern if used).
/api/health returns healthy and is wired into Render's health check.
Scheduled jobs (billing, outbox retry) verified to run exactly once across all backend instances.
Tenant-isolation and idempotency negative-test suites (Section 10) pass against the deployed environment, not just locally.
Monitoring/alerting is receiving data from the live environment before the domain is announced to real users.

9.1 Required Indexes
Unique index on users.email (normalized).
Unique index on each profile collection's user reference (milkmen, customers).
Unique index on milkmen.code.
Unique compound index on milk_records for (milkman_id, customer_id, date, shift, type) — the “logical delivery” guard.
Unique compound index on monthly_bills for (milkman_id, customer_id, month).
Unique compound index on idempotency_keys for (owner_scope, key).
Unique index on payments.receipt and on provider reference fields where present.
Unique index on whatsapp_outbox.event.
Unique index on admin_settings.section.
Compound indexes on (milkman_id, status/date) access paths across tenant-scoped collections, and on customer history lookups.
TTL indexes on registration_otps.expiry and idempotency_keys.expiry.
No collection shall embed unbounded arrays of historical records; histories are referenced, not embedded.
10. Testing Requirements and Definition of Done
10.1 Test Layers
Unit tests: calculations, validators, state machines, permission checks.
Repository tests: index enforcement, transactions, uniqueness constraints, aggregation correctness.
API tests: authentication, tenancy isolation, idempotency, concurrency.
Frontend component tests: accessible, localized components.
End-to-end tests: onboarding, route entry (online and offline), adjustments, billing/payment, product orders, disputes, admin flows.
Operational tests: load testing, dependency-outage handling, backup/restore, graceful shutdown, deployment rollback.
10.2 Mandatory Negative Test Cases
Milkman A requests milkman B's resources, across every resource family.
Customer A requests customer B's resources.
An admin without the required permission attempts a permissioned action.
A disabled/deactivated user attempts to reuse a previously issued token.
A request payload attempts to inject MongoDB query operators.
The same idempotency key is submitted twice with different request content.
Concurrent duplicate payment or delivery submissions.
A malicious CSV export payload attempting formula injection.
10.3 Definition of Done
A feature is done only when: behavior and acceptance criteria are agreed; API and data compatibility are documented; tenancy and permission checks are explicit and tested; responsive and accessible states are complete; tests are proportional to risk (per Section 10.1); safe telemetry exists (no PII leakage); rollback is possible; CI is green; security findings are triaged; and this SRS is updated to reflect the shipped behavior.

12. Appendix
12.1 Suggested KPIs
≥ 98% of deliveries entered same-day.
Median delivery entry time ≤ 10 seconds per customer.
Zero duplicate ledger writes.
≥ 99% of bills issued without correction.
≥ 99.5% payment-to-bill reconciliation rate.
Zero cross-tenant data-exposure incidents.
≥ 99.9% availability once the platform is mature.
12.2 Business Invariants (Cross-Cutting)
A customer belongs to exactly one milkman; every tenant-owned entity carries milkman_id.
Client-supplied tenant IDs are untrusted; the backend always derives/verifies tenant context server-side.
Rates and prices snapshot into deliveries/orders at the time of the transaction; later rate edits never rewrite historical records.
Money is represented in integer minor units or Decimal128, never native floating point, for any accounting value.
Instants are stored in UTC; service dates are interpreted in the configured timezone (Asia/Kolkata default).
Logical delivery, customer/month bill, scoped idempotency key, receipt, and provider event are each unique.
Soft-deleted ledger entries are excluded from totals but retained for history.
State changes validate both the current state and the requested target state.
Notifications are secondary; the committed ledger is always authoritative.
Audit history is append-only for ordinary users.
12.3 Final Acceptance Statement
GauAmrut is production-ready when: a milkman can onboard, connect and manage customers, complete daily routes online or with safe offline recovery, generate explainable bills, reconcile payments exactly once, manage products/orders/disputes, and export trustworthy reports; a customer can independently understand and act on their own records; and an administrator can operate the platform through least-privilege, audited controls — all of this running live on Vercel + Render + MongoDB Atlas, tenant-secure, mobile-accessible, localized, observable, backed up, recoverable, and correct under retries and concurrency.
